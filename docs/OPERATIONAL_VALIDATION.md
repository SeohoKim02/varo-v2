# Varo V2 운영 형식 검증

이 문서는 **새 기능 기록이 아니라 검증 기록**입니다. Varo V2를 실제 운영 업로드와 같은 형태의
익명화 데이터로 파일 업로드부터 추천 결과·화면 상태까지 처음부터 끝까지 실행하고, 나온 값을
그대로 적었습니다. 기능 설명은 [`docs/VALIDATION.md`](VALIDATION.md)·[`docs/ALGORITHM.md`](ALGORITHM.md)에
있고 여기서는 반복하지 않습니다.

측정 환경: Windows 10 / Python 3.11.0, 단일 데스크톱, 다른 부하 없음.
측정일 기준 커밋: `9f8ae15` 이후 작업 트리.

---

## 1. 검증 목적

1. 대용량 데이터 처리
2. 다중 점포·다중 상품·다중 DC 처리
3. 정상 행 · 유지 경고 행 · 제외 가능 오류 행이 섞인 데이터의 부분 적용
4. 제외 후 참조 관계와 데이터 무결성
5. 추천 실행과 VHS 최종 순위
6. DIRECT·VIA_DC 및 DC01·DC02 분리
7. 홈 · 추천 실행 · 경로 상세 · 분석 및 검증 · 데이터 관리의 상태 일치
8. 실제 화면의 이해도
9. 성능과 오류 안정성
10. 문서와 실제 구현의 일치

## 2. 익명화 데이터 구성

생성기: `tools/generate_anonymized_operational_workbook.py`
출력: `validation_data/varo_v2_anonymized_operational.xlsx` (0.27 MB)
기대값: `validation_data/varo_v2_anonymized_operational_manifest.json`

- **고정 seed 20260901**. 같은 seed면 시트 내용과 manifest가 완전히 동일합니다(테스트로 확인).
- **개인정보·실제 업체 정보 없음.** 모든 이름이 가상 명칭입니다.
  - 점포 `가상점포 01`~`가상점포 40`, DC `가상물류센터 1`·`가상물류센터 2`
  - 상품 `가상상품 01`~`가상상품 30`, 권역 `가상권역 A`~`가상권역 D`
  - 좌표는 실제 주소가 아니라 인공 격자(위도 10.x / 경도 10.x)입니다.
- 앱의 기본 샘플(`data/`, `samples/`)은 그대로 두었고, 이 파일이 기본 경로에 끼어들지 않습니다.

| 시트 | 행 수 | 비고 |
|---|---:|---|

| `products` | 30 | `product_id`는 **숫자 코드**(100001~100030) |

### 규모 선택 근거

무조건 큰 파일을 만들지 않고, 아래 실측 곡선을 보고 **한 대의 데스크톱에서 전체 흐름이 5초 안에
끝나면서도 수천 행을 다루는 40점포/30상품**을 기본값으로 정했습니다. 더 큰 규모도 정상 동작하며
그 수치도 함께 남깁니다(§9).

### 경로 구성

- 점포 간 DIRECT 경로는 양방향 전부(40×39 = 1,560행).
- 각 점포는 **자기 권역의 DC 한 곳**과만 연결됩니다(왕복 2행 × 40점포 = 80행).
  - DC01: 가상점포 01~20 · DC01 관련 경로 40행
  - DC02: 가상점포 21~40 · DC02 관련 경로 40행
- 이 구조 때문에 DC01 쪽 문제가 DC02 경로를 건드릴 수 없고, 그 반대도 마찬가지입니다.

| 구분 | 행 수 |
|---|---:|
| DIRECT | 46 |
| VIA_DC | 21 (DC01 8 · DC02 12 · DC 누락 1) |

## 3. 오류·경고·제외 구성

**파일 전체를 차단하는 오류는 0건입니다.** 문제 행을 제외하면 파일이 그대로 쓰일 수 있어야
부분 적용을 검증할 수 있기 때문입니다.

### 행 자체 문제로 제외되는 13행

| 시트 | 원본 행 | 문제 |
|---|---:|---|
| stores | 10 | `node_name` 비어 있음 (S07) |
| inventory | 42 | `stock_qty` 음수 |
| inventory | 122 | `stock_qty` = "십오" (숫자 변환 실패) |
| inventory | 202 | `store_id` 비어 있음 **＋** `stock_qty` 음수 → **한 행에 오류 2건, 제외는 1행** |
| inventory | 92, 963 | 같은 키·다른 값(값 충돌 중복) → 두 행 모두 제외 |
| inventory | 962 | 62행과 완전히 동일한 중복 → 뒤 행만 제외 |
| routes | 17 | `distance_km` 음수 |
| routes | 47 | `estimated_cost` = "미정" |
| recommendations | 65 | `recommended_qty` = 0 |
| recommendations | 66 | VIA_DC인데 `dc_id` 비어 있음 |
| recommendations | 67 | `route_type` = "경유" |
| recommendations | 68 | 출발지 = 도착지 |

`routes` 252행에는 **완전히 빈 행**을 넣어, 빈 행이 문제로 보고되지 않으면서 아래 행 번호도
밀지 않는지 확인했습니다.

### 연쇄 제외 106행

`S07`의 기준정보 행이 빠지면서 그 점포를 참조하는 행이 같은 정제 단계에서 제외됩니다.

- 재고 24행 · 경로 80행(DIRECT 78 + DC01 왕복 2) · 추천 1행(`R0063`)
- 존재하지 않는 점포 `S99`를 참조하는 추천 1행(69행)

### 유지되는 경고 4행

| 시트 | 행 | 경고 | 처리 |
|---|---:|---|---|
| products / inventory / recommendations | 각 2 | `product_id`가 숫자로 저장됨(`id_numeric`) | **경고만 표시 · 적용 데이터에 포함** |
| inventory | 62 | 완전 중복 쌍의 **첫 원본 행** | **유지**(뒤 중복행만 제외) |

경고가 있는 행 전체는 7행이고, 그중 3행(중복으로 제외된 행)을 뺀 **4행이 적용 데이터에 남습니다.**

## 4. 실제 사용자 흐름과 결과

검사는 앱과 같은 서비스 경로로만 진행했습니다. 테스트에서 내부 DataFrame을 만들어 부분 적용
서비스만 호출하는 방식은 쓰지 않았습니다.

```
파일 읽기(file_reader) → 원본 snapshot 보존 → 컬럼·값 정규화(data_loader)
→ 행 단위 문제 분류(data_issues) → 제외 대상 계산 → 참조 관계 연쇄 정리
→ usable data 생성 + 제외 후 재검증(partial_data) → pending 저장(prepare_pending_data)
→ 사용자 클릭으로 적용(commit_pending_data) → 사용자 클릭으로 추천 실행(run_applied_analysis)
```

### 4-1. 파일 검사 결과 (적용 전)

| 항목 | 기대값 | 실제 |
|---|---:|---:|
| 원본 전체 행 | 2,742 | 2,742 |
| 실제 적용 행 | 2,623 | 2,623 |
| 제외 예정 행 | 119 | 119 |
| 경고 행 | 7 | 7 |
| 유지 경고 행 | 4 | 4 |
| 파일 차단 오류 | 0 | 0 |
| 상태 | 확인 필요 | 확인 필요 |

테이블별 제외: `routes` 82 · `inventory` 30 · `recommendations` 6 · `stores` 1.
**제외된 원본 행 119개의 (시트, 행 번호) 집합이 manifest와 정확히 일치**했습니다(누락 0, 초과 0).

- 업로드만으로는 아무것도 적용되지 않았습니다(`varo_data` 없음, 추천 0건).
- 검사 결과는 `pending_*`에만 저장되고 현재 데이터와 추천은 그대로였습니다.
- 이미 적용된 데이터가 있는 상태에서 같은 파일을 다시 검사해도 `data_signature`와 적용 행 수가
  변하지 않았습니다. 검사 취소 시에도 마찬가지입니다.

### 4-2. 제외 후 남은 행

| 테이블 | 원본 | 제외 | 적용 |
|---|---:|---:|---:|
| stores | 42 | 1 | 41 |
| products | 30 | 0 | 30 |
| inventory | 962 | 30 | 932 |
| routes | 1,640 | 82 | 1,558 |
| recommendations | 68 | 6 | 62 |

제외 후 재검증 결과는 **통과**(오류 0)였습니다.
적용 데이터에는 음수 재고·변환 실패 값·빈 식별자·중복 키·수량 0·잘못된 경로 유형·자기 자신
이동이 하나도 남아 있지 않습니다.

### 4-3. 참조 무결성

- `inventory.store_id` ⊆ `stores.node_id`, `inventory.product_id` ⊆ `products.product_id`
- `routes.source_id/target_id` ⊆ `stores.node_id`
- `recommendations`의 출발·도착·상품·DC 참조 전부 유효
- DIRECT 추천 62건 중 경로가 없는 건 0건, VIA_DC 추천의 두 구간 경로 누락 0건
- **고아 참조 0건**
- 과도 제거 없음: 오류가 있던 `S07` 하나만 사라지고 나머지 41개 노드·30개 상품은 전부 남았습니다.

### 4-4. 데이터 적용

- `문제 행을 제외하고 사용` 버튼을 눌러야만 현재 데이터가 교체되었습니다.
- 적용 후 `pending_*`가 모두 정리되었고, 이전 추천·파이프라인 결과가 초기화되었습니다.
- 적용 직후 `analysis_run_required = True`(추천 실행 전 상태)이고 추천은 0건이었습니다.
- 원본 snapshot(`raw_data`)은 제외 전 962행 그대로 보존되어 원본 위치 추적이 가능합니다.

## 6. 추천 파이프라인 결과

> 이 절의 수치는 **알고리즘 강화 이전(`vhs-2.1` 이전)** 의 최초 검증 기록입니다. 강화 이후의
> 값과 변경 사유는 §13과 [`docs/ALGORITHM_BENCHMARK.md`](ALGORITHM_BENCHMARK.md) §14에 있습니다.
> 데이터 계층(§3–§5)의 수치는 강화 후에도 동일합니다.

추천은 **사용자가 `추천 실행`을 눌렀을 때만** 계산되었습니다.

| 항목 | 값 |
|---|---:|
| 후보 생성(적용된 추천 입력 행) | 62 |
| 추천 가능 | 60 |
| 최우선 추천 | 1 |
| 확인 필요 | 0 |
| 이동 불가(추천 전 차단) | 2 |
| 상태별 합계 | 62 = 전체 후보 수 |

- 차단된 2건은 생성기가 의도적으로 넣은 `R0061`·`R0062`이며, 이유는
  "출발 점포 재고보다 이동 수량이 많습니다."입니다. 최종 추천 목록에 없습니다.
- 제외된 원본 행에서 온 `R0063`은 후보 목록 자체에 존재하지 않습니다.
- 연결된 알고리즘 28개, 실행 오류 0건. 보류 2건은 설계상 보류입니다
  (`varo_sensitivity`, `vhs_reason` — 이력 보정 그룹 전제).

### 알고리즘 역할

| 알고리즘 | 역할 | 확인 |
|---|---|---|
| VHS | **최종 추천 순위** | `services.vhs_score_engine.apply_auto_vhs` 기준으로 최종 점수 산출 |
| Greedy | 기준선 비교 | `heuristic_optimizer.add_heuristic_scores` 연결, 순위 결정에는 미사용 |
| Pareto | 보조 검증 | `pareto_analysis` 산출됨 |
| DQN | 선택형 참고 | **자동 실행·자동 학습 없음**. 모든 후보 `dqn_action = 미연결`, `dqn_artifacts_read = False`, 학습 결과 없음 |

### 최우선 추천 (실제 결과 그대로)

| 항목 | 값 |
|---|---|
| 상품 | 가상상품 13 |
| 출발 → 도착 | 가상점포 13 → 가상점포 14 |
| 경로 유형 | DIRECT (경유 DC 없음) |
| 권장 이동 수량 | 60 |
| 이동 비용 | 6,500 |
| 예상 절감 효과 | 226,780 |
| VHS | 74.68 |
| 추천 신뢰도 | 66.0 (전체 신뢰도 상태 "보통") |
| 안정성 | "검토 필요" (일부 가중치 변화에서 상위 순위가 바뀔 수 있음) |

화면에 표시되는 추천 이유 3문장:

1. 재계산 VHS가 상위권이라 우선 검토할 수 있는 후보입니다.
2. 예상 절감액이 약 226,780원으로 재배치 효과가 기대됩니다.
3. 직접 이동 경로로 단순한 경로 구성입니다.

수량·절감액·비용은 모두 적용된 재고/경로 값에서 계산된 값이고, 계산할 수 없는 값을 0으로
표시한 항목은 없었습니다. 추천 60건 모두 이동 수량이 출발 점포 재고 이하입니다.

**결과를 보기 좋게 만들려고 데이터를 다시 손보지 않았습니다.** 안정성이 "검토 필요"로 나온 것도
그대로 남겼습니다.

## 10. 발견한 문제와 수정

### 수정 1 — 데이터 관리 페이지가 문제 있는 적용 데이터에서 예외로 죽음 (중대)

- 증상: 적용된 데이터에 행 단위 문제가 있고 문제가 5건을 넘으면 `데이터 관리` 페이지가
  `NameError: name 'detail_rows' is not defined`로 렌더링에 실패했습니다.
- 원인: `pages/data_management.py`가 `detail_rows`를 import하지 않은 채 호출.
- 영향: 이번 검증처럼 **부분 적용을 실제로 사용하는 경우에만** 발생. 문제가 없는 기본 샘플만
  쓰던 기존 테스트에서는 재현되지 않았습니다.
- 수정: `services.data_issues.detail_rows` import 추가(최소 수정).
- 회귀 방지: `tests/test_operational_ui_flow.py`가 문제 있는 데이터로 5개 페이지를 실제 렌더링합니다.

### 수정 2 — 후보 생성이 첫 번째 DC만 사용함 (다중 DC 결함)

- 증상: 추천 시트가 없는 업로드에서 후보를 생성할 때 `services/candidate_generator.py`가
  DC 목록 중 **첫 번째 DC만** 사용했습니다(`dc_ids[0]`). 그래서 DC02로만 연결되는 구간은
  DC 경유 후보가 아예 만들어지지 않고 후보에서 사라졌습니다.
- 재현: 두 DC가 있는 이 워크북에서 `S25 → S30`(둘 다 DC02 권역)의 직접 경로를 제거하면
  수정 전에는 경로 해석 결과가 `None`, 수정 후에는 `VIA_DC / DC02`가 나옵니다.
- 수정: `_store_ids_by_type`이 DC 전체를 반환하고, `_resolve_route`가 모든 DC를 평가해
  **가장 저렴한 경유 경로**를 고릅니다. 직접 경로와 경유 경로 중 싼 쪽을 고르는 기존 판단 기준은
  그대로이고 알고리즘의 의미를 바꾸지 않았습니다. 선택된 DC가 후보의 `dc_id`/`dc_name`에 반영됩니다.
- 회귀 방지: `tests/test_operational_validation.py::MultiDcTests::test_candidate_generation_uses_every_dc_not_only_the_first`

### 수정 3 — 문제 표가 행 수 제한 없이 그려짐

- 증상: 문제가 100건이 넘으면 데이터 관리의 "전체 문제 보기"·"전체 제외 행 상세" 표가 전부
  렌더링됐습니다(이번 데이터는 문제 항목 100건 이상, 제외 행 119건).
- 수정: 화면 표를 200행에서 끊고 전체는 CSV로 안내(`_ISSUE_TABLE_LIMIT`).

### 수정하지 않은 관찰

- `services/home_state.py`의 `warning_count`는 계산만 되고 어느 페이지에도 렌더링되지 않습니다.
  화면에 보이는 값이 아니므로 이번 범위에서는 건드리지 않았습니다.

## 12. 추천 실행 진행 표시 (후속 작업)

§11에서 "대기 중 피드백이 없다"고 남긴 한계를 해결한 뒤 다시 측정한 기록입니다. **추천 결과는 하나도

### 실제 단계와 진행 값

## 16. 실행 이력 Shadow 운영 검증

익명 운영 데이터의 동일 실행계획을 표준 SQLite 이력 서비스에 기록하고 다음 흐름을 검증합니다.

1. 검증된 계획을 사용자 동작으로 1회 기록
2. 같은 `plan_id`의 두 번째 저장 차단
3. 서로 다른 항목을 실행·일부 실행·미실행으로 기록
4. 실제 수량과 선택형 미실행 사유, 익명 사후 결과 입력
5. 새 DB 연결로 계획과 항목 재조회
6. 현재 적용 데이터를 초기화한 뒤에도 과거 이력 재조회
7. UTF-8 BOM CSV 내보내기와 로컬 DB 경로 미포함 확인
8. 이력 기록 전후 후보 수·계획 수·수량·비용·절감·순효과·항목 배열 동일 확인

운영 검증은 프로젝트 런타임 DB가 아니라 매 실행마다 생성되는 임시 익명 DB를 사용합니다. 따라서 실제
점포 이력이나 로컬 운영 DB를 검증 산출물에 포함하지 않습니다. 실제 결과 표본이 없는 항목은 오차 0으로
계산하지 않으며 표본 수 0과 `계산 불가`로 유지합니다.

최종 실행에서는 저장 backend 확인을 포함해 전체 **187개 항목이 통과**했고 실패는 0건이었습니다. 계획 1건과 이동 56건을 기록한 뒤
3건의 상태를 확인했으며, 실제 비용·절감·순효과 비교 표본은 입력한 1건만 집계했습니다. CSV는 계획의
56개 이동을 UTF-8 BOM으로 내보냈습니다. 이력 기록 전후에도 후보 58건, 실행계획 56건·2,985개,
비용 812,746.67원, 예상 절감 6,541,465.33원, 순효과 5,728,718.67원이 동일했습니다.

## 17. SQLite/PostgreSQL 저장 계층 검증

기본 운영 검증은 외부 DB 설정 없이 명시적인 임시 SQLite를 사용합니다. 저장 backend가 `sqlite`인지
추가 확인하고, 실행계획을 계산하는 동안에는 DB 쓰기를 하지 않으며 사용자가 기록할 때만 plan과 items를
저장합니다. PostgreSQL adapter 추가 뒤에도 운영 fixture의 후보·계획·수량·비용·절감·순효과 기대값은
변경하지 않았습니다.

3회 측정 중앙값은 읽기 0.276초, 검사 준비 0.844초, 적용 0.028초, 추천 분석 3.732초, 전체 4.883초였습니다.
저장소 조회·기록은 추천 후보 계산 루프에 들어가지 않으며, 계획 기록은 사용자 버튼을 누른 뒤에만 실행됩니다.

실제 PostgreSQL 서버는 이 검증 환경에 없어 네트워크 연결 성공을 주장하지 않습니다. 대신 격리된
DB-API contract 검증으로 다음을 확인합니다.

- PostgreSQL용 `CREATE TABLE IF NOT EXISTS`, schema version, PK/FK와 인덱스
- 값의 `%s` parameter binding, 같은 plan 중복 차단, 항목 수정 시 row lock
- plan+items와 result+audit의 commit/rollback, 연결 종료, NULL·UTC 문자열·float 의미
- SQLite/PostgreSQL 조회 결과와 calibration CSV 컬럼·값의 parity
- PostgreSQL 설정 후 연결/조회/쓰기 실패 시 로컬 SQLite를 만들지 않는 정책
- SQLite source hash를 보존하는 dry-run·중복 감지·원자 이관·건수 재검증

실제 서버 통합 검증은 배포 전 별도의 비운영 test database를 제공받은 경우에만 수행해야 합니다. 운영 URL을
pytest에 전달하거나 기존 운영 schema를 초기화하는 방식은 사용하지 않습니다.
